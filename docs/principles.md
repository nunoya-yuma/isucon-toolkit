# 原則とレビューの観点

このリポジトリと、これを使う大会リポジトリを作り直すときの原則と、PRで確かめる観点。

**目的**：初期構築の段ごとに、誰が何をしているか、どこまで進んだか、止めたらどうなるかを、チームの誰でも（人間でもAIでも）すぐ分かるようにする。速く終えることより、各段で状況を共有して早めに課題を見つけることを優先する。初期構築は時間がかかり、つまずきやすく、メンバーごとに手順や道具が違うためである。

各原則の後ろの［確度］は、たたき台の時点での自信の度合い。「高」は経験から言えるもの、「中」は筋は通るが検証していないもの、「要議論」はトレードオフがあり決めていないもの。

## 原則

### 1. 見れば分かる（自明である）［高］

細かい規則を全員が読んで覚えている前提にしない。一般的な慣習に沿った構成・命名にし、READMEから辿れば今の中身が分かるようにする。独自の仕組み（エージェント間の連絡、承認表など）は各自の内側に閉じ、共有するリポジトリはGitの普通の使い方だけで読めるようにする。

### 2. 名前は1台に1つ［高］

1台のサーバーを、EC2のNameタグ・SSHのalias・`hosts/<名前>/`・inventory・文書のすべてで、同じ文字列で呼ぶ。名前が複数あると、設定の上書きが黙って効かない、指示の対象を取り違える、といった事故になる。

### 3. mainが正しい記録［高］

実機に入っているものは、mainのどれかのcommitだと言える状態を保つ。作業は短命の話題branchで行い、PRでmainへ入れる。実機を直接書き換えたら、その区切りでcommitするか、元に戻す。実機がどのcommitか、Git外の変更がないかを、1つのコマンドで確かめられるようにする。

### 4. 実機の写しは、大会が変わっても同じ形［中］

大会リポジトリでは、実機から取り込んだ設定を、実機の絶対パスのまま`server/`の下に置く（例：`server/etc/nginx/nginx.conf`）。台ごとに違うものだけを`hosts/<台の名前>/`に置く。製品ごと・目的ごとのフォルダ（`infra/nginx/`など）には分けない。どのファイルが実機のどこに入るかを、規則を読まずに推測できるようにするため。

未決：配備がアプリのフォルダそのものをcloneにする前提のため、リポジトリ直下にアプリのファイルと`docs/`などが並ぶ。直下の構成は「構成の案」で決める［要議論］。

### 5. タスクは1つの入口で1つのこと［高］

配備は配備だけ、benchmarkはbenchmarkだけを行う。複数のタスクを順に呼ぶ入口を作る場合も、中の各タスクを単体で実行できるようにする。名前は動詞にそろえる（`status`・`snapshot`・`deploy`・`bench`・`logs`・`reboot`など）。

### 6. タスクは同じ形で振る舞う［中］

すべてのタスクに、次をそろえる。詳細は「タスクの共通の仕様」で決める。

- 実機を変えるかどうかを、helpとREADMEに書く（読取りだけ／実機を変える）。
- 前提を満たさなければ、何も変えずに止まる。
- 実機を変えるタスクには、変える前に差分を見る手段（plan）と、戻す手段（restore）を付ける。
- 結果を、機械が読める形と1行の要約で、決まった場所に出す。終了コードの意味をそろえる。
- 途中で止まったとき、どの段まで進んだかが分かる。

### 7. 変更は、区切りごとに1行で伝わる［中］

人が知る必要のある変更は、チーム全員が見る場所に「誰が・どの台・何を・どのcommit・戻し方」の1行で出す。1行で書けない変更は、区切りが大きすぎる合図とみなす。

### 8. mainには動作実績のあるものだけ［高］

mainに入れるタスクは、どの環境で・いつ・どのcommitで動かしたかを、PRとREADMEに書く。成熟度は次の4段階で表す。

| 段階 | 意味 |
|---|---|
| 0 | 書きかけ。通して動かしていない |
| 1 | 手元（docker等）で動いた |
| 2 | 大会の実機かそれと同等の環境で動いた |
| 3 | 大会や言語が変わっても、設定の変更だけで動いた |

### 9. 公開リポジトリには、一般的なものだけ［高］

このリポジトリはpublic。競技中はpushしない。大会ごとの値（パス・サービス名・ホスト名・IP）は大会リポジトリ側の設定に置き、ここには書かない。競技中の修正は、大会リポジトリに複写した側で行い、汎用的なものだけ競技後に戻す。そのため、複写しても動く（置き場所に依存しない）ことを求める。

## PRで確かめる観点（チェックリスト）

PRの説明に、該当しない項目は「該当なし」と書く。

**自明さ**
- [ ] READMEから辿って、追加・変更したものに行き着けるか
- [ ] 名前（ファイル・タスク・台）は既存のものとそろっているか。同じものに別の名前を付けていないか
- [ ] 一般的な慣習で読めるか。独自の規則を知らないと読めない箇所はないか

**タスクの形**
- [ ] 1つの入口で1つのことをするか
- [ ] 実機を変えるかどうかを書いているか
- [ ] 前提の確認・plan・restore・結果の出力があるか（実機を変えるタスクの場合）
- [ ] 途中で止めたときの状態を説明できるか

**安全**
- [ ] 大会の情報・IP・秘密値・鍵が入っていないか
- [ ] 大会のルールで触れてはいけないもの（環境確認の仕組み・運営のユーザーや鍵など）に触れていないか
- [ ] サービスを意図せず再起動しないか

**動作実績**
- [ ] どの環境・いつ・どのcommitで動かしたかを書いているか。成熟度はいくつか
- [ ] `shellcheck`などの機械的な検査を通したか

## 次に決めること

1. 構成の案：フォルダ・branch・命名・タスクの一覧（原則4の未決を含む）
2. タスクの共通の仕様：入口・出力の形・終了コード・中断と復元
3. 既存の道具（`scripts/`・`contest-ops/`・各自の手持ち）の移行：1タスクずつ、同じ機能が2つあれば1つに絞る
