# 構成の案

[原則](principles.md)に沿って、このリポジトリと大会リポジトリの形を決める案。たたき台の段階で、決めた点と、小さな実地テストで確かめる点を分けて書く。

## 0. 前提にした事実（2026-10の時点）

この案を作ったときの事実。今の成熟度と動作実績の正本はREADMEの表で、この章は更新しない。

2026-10の練習で、既存の道具を棚卸しし、実機で小さく試した結果（詳細は各自の大会リポジトリの記録）。

- 実機で最後まで通した実績があるのは、`scripts/`の`deploy.sh`・`logs.sh`・`profile.sh`・`final-check.sh`（1人の練習で、取り込み→計装→改善→2つ目のインスタンスへのDB移設→最終確認まで）。dockerで動くアプリでも`deploy.sh`は最後まで通った。
- `contest-ops/`のうち実機で通したのは、`inspect`・`snapshot`・`nginx-plan/apply/restore`・`reboot`。`deploy`・`rollback`・`configure`は実機の実績がない。
- 実機へコードを渡す3つの経路は、どれも動いた。(1) 手元からSSHで、実機の**受信用のbare repo**へ`git push`し、アプリのrepoがそこからfetchする。(2) git bundle。(3) 読取り専用のdeploy key。(1)は、受け側の所有者の違い（ログインはubuntu、アプリのrepoはisucon）を最初に1回整える必要があった。稼働中のアプリのrepo（non-bare）へ直接pushする経路は試していない。
- 複数のインスタンスへ続けて配って1つのインスタンスだけ止まったとき、各インスタンスの「HEAD・未commitの変更の有無」を並べるだけで、どこまで進んだかを判別できた。
- 確認系のタスク（`verify`・`final-check.sh`）の失敗は、どれも大会ごとの前提の違い（HTTPのHost、追従するbranchの指定、DBの認証）が原因だった。`verify`には、HTTPの確認に任意のHostを渡す設定がまだない。`final-check.sh`は実機で`git fetch`を行う（refが変わる）。

## 1. 推奨する方式（要約）

| 論点 | 推奨 | 一言の理由 |
|---|---|---|
| 入口 | 1つのCLI `tk <task> [インスタンス...]`。中身はタスクごとに既存の実装を呼ぶ | 使う人は実装の技術を意識しない。既存の実績を捨てない |
| 実装の技術 | bashを基本に、実績のあるAnsibleのタスクは残す | 依存を増やさず、動いたものを使う |
| deployの出所 | **必ずcommitから配る**。branchを指定しても、開始時に1度だけ完全なSHAへ解決し、全インスタンスへ同じSHAを配る | 出所は常にSHAで追える。途中でbranchが進んでもインスタンスごとに違うものを配らない |
| 実機へ渡す経路 | 手元からSSHで、各インスタンスの受信用のbare repoへpush。アプリのrepoは、lockの中でそこからSHAを指定してfetchする。同時にGitHubへもpushする | 実機に鍵を置かない。試した経路そのもの。Gitの既定の安全装置（稼働中のbranchへのpushの拒否）を外さない |
| 状態 | `tk status`を最初に作る。checkoutの状態・直近の操作・稼働の確認・GitHubでの公開を、別の事実として並べる | 実機の状態を信頼できることが、最も重要な目標 |
| 操作の記録と排他 | 実機を変える`tk`のタスクは、実機側の同じlockを使う。操作の開始・段・終了を実機に書く | 他のPCからの`tk`の操作と衝突しない。途中で止まっても、どこで止まったかが残る |
| 戻し方 | 自動のrollbackは後回し。ただし手で戻すための記録（変更前のSHA・触った宛先・元のファイルの退避・戻せない操作）は最初から残す | 失敗したとき「何が変わったか」が分からないのが最も困る |
| インスタンスの名前 | 1つのインスタンスに1つ。Nameタグ・SSHのalias・`hosts/`・設定・文書で、既存の識別子と一意に対応させる | 原則2 |
| branch | `main`＋短命の`feat/<話題>`。個人の統合branchは置かない | 原則3、一般的な形 |

## 2. 2つのリポジトリの形

### 2.1 このリポジトリ（public）

最終の形：

```text
isucon-toolkit/
├── README.md            # 入口。タスクの一覧・成熟度・最初の手順
├── tk                   # 唯一の入口（bash）。tk help でタスクの一覧
├── tasks/               # タスク1つにつき1ファイル（tk が呼ぶ）
├── lib/                 # 共通の部品（設定の読込み・実機側のlockと操作の記録・出力）
├── contest-ops/         # Ansible。tk から呼ぶタスク（snapshot・nginx・reboot）
├── templates/           # 大会リポジトリに複写するひな形（設定・.gitignore・README）
├── docs/
│   ├── principles.md
│   ├── design.md        # この文書
│   ├── tasks.md         # タスクの共通の仕様（次の成果物）
│   └── runbook.md       # 競技の流れ。tk のタスクを順に並べる
└── tests/
```

移行の途中は、`scripts/`と`contest-ops/`の既存の入口をそのまま残す。`tk`へ移したタスクから順に、READMEの一覧を`tk`に切り替え、元の入口を消す。同じ機能の入口が2つある期間を、READMEで明示する。

`contest-ops/`の`deploy`・`rollback`・`configure`・`verify`・`bootstrap`は、`tk`から呼ばない。消すか残すかは、作者と相談して決める。残す場合は、READMEに「tkの対象外」と書く。

### 2.2 大会リポジトリ（private、大会ごと）

```text
<大会repo>/              # = 実機のアプリのフォルダ（例：/home/isucon/webapp）のclone
├── README.md            # 大会の要点・インスタンスの役割・今の状態の見方（templates から）
├── go/ sql/ ...         # アプリ（実機から取り込んだまま）
├── server/              # 全インスタンスに配る設定。実機の絶対パスのまま（etc/nginx/... など）
├── hosts/<インスタンスの名前>/    # そのインスタンスだけの設定（server/ より優先）
├── tk.env               # 大会ごとの値（パス・サービス名・インスタンスの名前と役割・確認先）
├── tools/toolkit/       # このリポジトリの複写（固定SHA、SOURCE.md付き）
└── docs/                # 大会の記録（状態・結果・知見）
```

- リポジトリの直下＝実機のアプリのフォルダとする。直下にアプリと管理用のファイルが並ぶが、実績のある形で、実機のパスとの対応が最も単純になる。
- `server/`には、アプリのフォルダの下のパスを置かない（原則4）。
- 動いているデータ（DBファイル・lock・アップロード）は、`templates/`の`.gitignore`の例に入れ、取り込みの前に列挙する。
- 結果の記録（`runs/`）は、`.gitignore`で除く。1行の要約を、チームのDiscordの決めた場所へ貼る（原則7）。

## 3. 名前

- インスタンスの名前は、**運営が付けたEC2のNameタグをそのまま使う**。本番ではNameタグは運営のCloudFormationが決め、変えると環境の確認（運営の環境確認の仕組み）が失敗するおそれがある。SSHのalias・`hosts/`・`tk.env`の`TK_HOSTS`・文書のすべてで、Nameタグと同じ文字列を使う（ハイフンを含んでよい）。
- マニュアルが示すホスト名（例：`<アプリ>-1.t.isucon.dev`）は別の名前として残る。大会リポジトリのREADMEに、Nameタグとの対応を1か所だけ書く。
- 練習で自分でインスタンスを作るときも、本番と同じ形のNameタグを付ける。
- SSHの入口を作るscriptは、指定した名前をそのままaliasにする（接頭辞を付けない）。
- タスクの名前は、1語で何をするか分かるもの（原則5）。

## 4. タスクの一覧

| タスク | 何をする | 実機を変えるか | 実装 | 作る回 |
|---|---|---|---|---|
| `status` | 各インスタンスについて、checkoutの状態・直近の操作・稼働の確認を、別の事実として1表に（tasks.mdの7章） | 読取りだけ | 新規（試作あり） | **作る** |
| `deploy` | 指定のcommitを、指定のインスタンスへ（tasks.mdの8・12章） | 変える | `scripts/deploy.sh`を改修 | **改修（1つのインスタンスから）** |
| `snapshot` | 原本の保全とインスタンスの情報の記録 | 読取りだけ | contest-ops `snapshot`・`inspect` | 既存の入口のまま |
| `init` | 実機のアプリのフォルダを大会repoのcloneにし、記録の領域と受信用repoを作る | 変える | 作らない。runbookの手順で行う | 作らない |
| `bench` | **練習専用**。benchmarkのインスタンスでbenchmarkを1回実行し、結果をjsonと1行に | benchmarkの初期化で変える | 新規（試作あり） | 後で |
| `logs` | ログを区切る（clear）・集計する（analyze） | clearは変える | `scripts/logs.sh` | 既存の入口のまま |
| `profile` | pprofを採る | 読取りだけ | `scripts/profile.sh` | 既存の入口のまま |
| `tools` | 解析の道具を入れる | 変える | `scripts/install-tools.sh` | 既存の入口のまま |
| `nginx` | nginx.confの値をplan・apply・restore | 変える（戻せる） | contest-ops `nginx-*` | 既存の入口のまま |
| `reboot` | インスタンスを1つずつ再起動し、戻るのを待つ（tasks.mdの14章） | 変える | 新規（`contest-ops`の`reboot`は包まない） | 2回目 |
| `final-check` | 最終のbenchmarkの準備ができているか（tasks.mdの13章） | 読取りだけ | `scripts/final-check.sh`を元に新規 | 2回目 |

`contest-ops`の`reboot`は、事前の検査と事後の確認でdeploy用の設定を求めるので、包まずに、`tk reboot`を小さく作る（2回目の範囲）。

## 4.1 benchmarkの扱い

本番では、benchmarkはポータルから人が流す。benchmarkのインスタンスは手の内にない。そのため、`tk`のどのタスクも、benchmarkのインスタンスへの接続を前提にしない（`bench`は練習専用）。人がbenchmarkを流す前後は、次の区切りで`tk`を使う。

```text
tk status → tk logs clear → （人がポータルでbenchmark） → tk logs analyze → tk status
```

SSHの入口を作るscriptも、benchmarkのインスタンスを任意にする。

## 5. deployの考え方

段・記録・置き場所・終了コードは、[タスクの共通の仕様](tasks.md)の7・8・12章が正。この章は、その形を選んだ理由だけを書く。

- **SHAを1回だけ決める**：branchを指定しても、開始時に1度だけ完全なSHAへ解決し、全インスタンスへ同じSHAを配る。途中でbranchが進んでも、インスタンスごとに違うものを配らないため。
- **作業ツリーからは配らない**：速い変更も、使い捨てのbranchへcommitして同じ`tk deploy`で配る。出所が常にSHAで追えるようにするため（原則3）。正規の手順と例外を分けない。
- **受信用のbare repoを通す**：稼働中のアプリのrepoへ直接pushしない（Gitの`receive.denyCurrentBranch`の既定の拒否を外さない）。pushは稼働中のものを変えないのでlockの外、fetchとSHAの照合と切替はlockの中で行う。
- **変更の前に、戻す手順を書く**：上書きするファイルを退避し、`recovery`を変更の前に記録する。どこで止まっても、人がそれを読んで戻せるようにするため（自動のrollbackはしない）。
- **lockは`tk`の中だけ**：同じ実機のlockを使うのは、`tk`の実機を変えるタスク。`tk`を通らない操作は排他できず、`status`の「未commitの変更」や「不一致」で後から気づけるだけである。

## 6. 代替案とトレードオフ

| 論点 | 代替案 | 利点 | 欠点 |
|---|---|---|---|
| deployの出所 | 手元の作業ツリーを送る（contest-opsの方式） | commitの手間がない | 出所が残らない。他の人が状態を信頼できない。最も重要な目標と衝突する |
| 実機へ渡す経路 | 実機がGitHubからfetch（deploy key） | 受信用のrepoが要らない。実績がある | 実機に秘密鍵を置く |
| 実機へ渡す経路 | git bundle | 鍵が要らない | 配るたびに作って送る手間 |
| 実機へ渡す経路 | 稼働中のアプリのrepoへ直接push（`updateInstead`など） | 受信用のrepoが要らない | Gitの安全装置を緩める。試していない |
| 複数のインスタンス | Ansibleで並行に | 速い | 実績がない。依存が増える |
| 直下の構成 | アプリを`webapp/`などに分ける | 直下が整理される | 実機のパスとの対応が1段複雑になる。実績がない |
| 実装 | 全部bashに書き直す | 依存が最小 | 実績のあるAnsibleのタスクを作り直す手間 |

### 6.1 複数のインスタンスとAnsible（設計選択の背景）

複数のインスタンスへの`deploy`も、Ansibleではなく、手元の`tk`が各インスタンスへSSHで同じ処理（`lib/remote.py`）をインスタンスを1つずつ流す形にした（2026-10-30）。

- Ansibleの強みは、複数のインスタンスを並行に処理できること、インスタンスごとの結果が最後に一覧で出ること、inventoryの組で対象を選べること。
- 今回は「インスタンスを1つずつ配り、`ok`でなければ止める」と決めたので、並行の強みは使わない（Ansibleでも`serial: 1`と`any_errors_fatal`で同じ動きになる）。インスタンスごとの結果は、`tk`の最後の1行の要約で足りる。
- `tk`の、1つのインスタンスへの`deploy`は実機で成熟度2になっている。`contest-ops`の`deploy`は実機の実績がなく、手元の作業ツリーを送る方式で、commitからだけ配る原則と合わない。Ansibleを全員の手元に入れる負担（9章のH5）も、まだ確かめていない。

**記録とlockの範囲**

- **必須**：`tk`自身の操作は、実機の上の共通の記録（`/var/lib/tk/ops/`）とlockを使う。後から別の人が`tk status`や`sudo cat`で、誰が何をしたかを追えるようにするため。
- **他の道具や手作業は自由**。`tk`の約束に合わせる必要はない。実機を変えたら、原則7の1行で知らせ、次の区切りまでにcommitして配り直す（原則3）。アプリのrepoへの変更は、`tk status`の「dirty」「不一致」で見える。Gitの外の設定（`/etc`など）の変更は、`status`では見えない（「設定の実物：未照合」）。
- **推奨**：繰り返し使う共有の道具を新しく整備するときは、`tk`に入れるか、同じ記録を残す形を相談する。`tk`を通らない道具で実機を変え続けると、その変更は記録に現れず、別の人が引き継ぎにくくなる（2026-10の練習でも、この形で混乱した）。

並行のdeployなどでAnsibleを使う必要が出たときの統合の案（必須ではなく、選べる形として残す）：Ansibleを「運ぶ役」にとどめ、実機での処理は`tk`の`lib/remote.py`（または同じ記録とlockを使う処理。形はtasks.mdの3〜5章）を呼ぶ。

この範囲は、導入と前半戦での実績を優先して、規則を最小にしたもの。実績がたまり、共有の道具を`tk`に寄せる価値が見えた時点で、推奨を必須に上げるかを見直す。

## 7. 初回の半日で作る範囲と受入条件

**作る**

1. `tk`の入口と`lib/`（設定の読込み・実機側のlockと操作の記録・1行の出力）
2. `status`（tasks.mdの7章）
3. 1つのインスタンスへの`deploy`（tasks.mdの8章。受信用のbare repoの準備はrunbookの手順）
4. README（`tk`のタスクと、まだ既存の入口のタスクの一覧・成熟度・最初の手順）

**受入条件**（ここまで動けば止めてよい）

- 1つのインスタンスに、使い捨てのbranchのcommitを`tk deploy`で配り、`tk status`でcheckout・直近の操作・稼働の確認が正しく出る。
- buildをわざと失敗させたとき、操作の記録が失敗した段を示し、`status`が「不一致」を出し、記録の手順で手で戻せる。
- 2つの手元から同時に`tk deploy`したとき、片方がlockで止まり、相手の操作IDを表示する。

**作らない（既存の入口のまま）**：`snapshot`・`logs`・`profile`・`tools`・`nginx`。

**2回目（初回の受入条件を満たした後）**：複数のインスタンスへの`deploy`・`final-check`・`reboot`（tasks.mdの12〜14章）。`init`はタスクにせず、runbookの手順で行う。`bench`は練習専用で、後で。

## 8. 本番の後に回してよいもの

- 配った設定（`server/`）と実機の実物の差の照合（`status`の拡張）
- 複数のインスタンスへの並行のdeploy
- 自動のrollback（手で戻すための記録は最初から残す）
- 実機の全体のprovision（パッケージ・カーネルの設定など）
- Discordへの自動の投稿。webhookはサーバーのチャンネルにだけ作れ、グループDMには作れない（botもグループDMに参加できない）。自動にするなら、チームだけのサーバーとチャンネルを作り、webhookのURLを秘密の値として各自の手元に置く。自分のアカウントのtokenで投稿する方法は、Discordの利用規約が禁じるself-botにあたるので使わない

## 9. 小さな実地テストで確かめる仮説

| 仮説 | 確かめ方 |
|---|---|
| H1 2台のPCから、同じインスタンスの受信用のbare repoへpushしても、所有者・groupの調整は最初の1回で足りる | 2つの手元から、同じインスタンスへ順に`tk deploy` |
| H2 実機側のlockで、2つのPCからの同時の`tk deploy`の片方が止まる | 2つの手元から同時に`tk deploy`（受入条件と同じ） |
| H3 `tk status`が、3つのインスタンスで10秒以内に返る | 3つのインスタンスで実行して時間を測る |
| H4 準備ができるまで待つ確認で、deployの成否の表示が正しくなる | dockerのアプリで`tk deploy`し、表示とappの応答を比べる |
| H5 チームの各自の手元に、Ansibleを入れる負担が問題にならない | 各メンバーに、`contest-ops`の`validate`を手元で通してもらう |
| H6 dockerのアプリで、buildの重複をなくせる | unitの`--build`に任せる設定と、buildの指定を残す設定で`tk deploy`し、時間と結果を比べる |
| H7 build失敗の後、記録の手順だけで手で戻せる | 受入条件の2つ目 |

## 10. 未決の論点

- `contest-ops/`の使わないタスクを消すか残すか（2.1）
- 原則8の基準が、早い共有を妨げないか（`status`と`deploy`を作る過程で確かめる）
